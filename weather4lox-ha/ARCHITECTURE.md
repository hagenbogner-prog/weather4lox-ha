# Weather4Lox HA architecture

## Provider model

Exactly one weather provider is active at runtime: `dwd` or `openweathermap`.
The app consumes Home Assistant weather entities and does not call provider APIs directly.

Each provider has its own fetch/cache policy. The requested forecast horizon is capped at seven days, but the app records and exposes the actual forecast length and source resolution returned by Home Assistant.

## Data flow

Provider entity -> provider adapter -> normalized forecast -> atomic cache -> Loxone Format 2 and optional HA entity publication.

Loxone requests on TCP port 6066 never trigger a provider API call when a usable cache exists.

## Cache rules

- Successful refresh builds a complete replacement cache and atomically swaps it in.
- Failed refresh preserves the last successful cache.
- Cache metadata includes provider, entity, source resolution, requested and actual forecast range, timestamps, and fallback status.
- Synthetic weather values are not generated by default.

## Home Assistant entities

Home Assistant add-ons cannot register arbitrary native entities through the Supervisor REST API. Optional MQTT discovery is used for standalone sensors when the HA MQTT integration is installed. Loxone service operation does not depend on MQTT.
